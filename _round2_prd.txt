
The Money Leak Round 2 Maximum Score PRD
Three hour hackathon build plan aligned to the judging rubric
Build LeakLens, a manager decision system that finds revenue leakage, predicts or prioritizes at-risk records using a model trained by the team on the provided dataset, explains the evidence, and records a measurable next action. The product must not be a generic dashboard: every screen must support a business decision and every numerical claim must be traceable to verified fields.

3 Schema first data contract
Before coding modeling logic, inspect every supplied CSV. Capture exact filenames, row counts, column names, types, null rate, date coverage, unique identifiers, category/status values, and five sample records. Choose only concepts proven by the files; never assume fields named order_id, revenue, price, cost, customer_id, or stock.
Select a base grain: transaction, order line, daily SKU, or inventory snapshot. Report this grain beside every metric.
Map verified keys and validate dimensions are unique before product/customer/campaign joins. Use left joins from the base table and show unmatched percent and row-count change.
Normalize strings and parse dates with errors captured. Do not silently drop rows or duplicate transaction value during joins.
Feature-gate every metric, rule, chart, and model. If required data is missing, show Unavailable with the reason.

Preferred path for maximum points: a supervised model trained on the supplied data, if verified status labels exist. This is a model built and fitted by the team on hackathon data. Do not use an LLM/API as the predictor. A pretrained model, embeddings, or API-only scoring should not be presented as the core model.
Recommended model for this hackathon
Use Logistic Regression as the required baseline and Random Forest Classifier as the recommended final model. Random Forest is the best practical choice for this project because it trains quickly on a normal CPU, handles nonlinear patterns and mixed numeric/categorical business features after encoding, needs little tuning, and provides understandable feature importance. It does not require the RTX 2050 GPU or CUDA. Limit the first demo model to roughly 100 to 200 trees, fixed random seed, and class weighting only if the risk class is rare. Use HistGradientBoosting only as an optional comparison if Random Forest is already working; do not spend hackathon time on GPU or deep-learning setup.
5 Leakage safe modeling specification
Step
Requirement
Target definition
Use only an inspected status/outcome field. Define eligible population and positive labels explicitly, e.g. returned/cancelled/refunded values found in data. Exclude unknown/ambiguous statuses.
Feature eligibility
Use information available before the target outcome: product/category, region/customer segment, quantity, order weekday/month, verified discount ratio, prior product rate, inventory state only if time-aligned.
Leakage exclusion
Never use post-outcome status, refund amount, return reason recorded after return, or final realised revenue as a predictor of the return/cancel label.
Split
Prefer train on earlier dates and test on later dates. If no viable dates, use stratified train/test split with fixed random seed. Never evaluate on training data.
Pipeline
Impute missing numeric values from train set; one-hot encode categorical values; fit transforms on train only; use a pipeline to avoid leakage.
Baseline
Majority-class prediction plus a simple business rule. The final model must improve a relevant metric or be retained only as an honest experimental result.
Threshold
Choose a probability threshold using validation data and business objective, e.g. prioritize precision for costly interventions or recall for expensive missed returns. State the choice.

9 Acceptance criteria
The app runs locally from a documented command and supports inspected CSVs without hard-coded column assumptions.
The data trust panel shows mappings, base grain, selected files, join health, and warnings.
If labels are eligible, a model is trained on the supplied data during the demo and its artifact/metrics are produced reproducibly.
A baseline and held-out evaluation are visible, with the selected decision threshold and reason.
The model is protected from obvious target leakage and uses only documented eligible features.
The priority queue leads to a segment/order/product investigation with transparent explanations and an action card.
All inferred financial values are labelled Estimated; unsupported concepts are unavailable, not fabricated.
A two-minute demo can move from raw data to manager action and validation metric without leaving the app.

11 Presentation script
“Managers do not need another sales chart; they need to know which leak to act on first. We first profile the provided data and show the analysis boundaries. We train our own model on the verified outcome field and compare it with a baseline on held-out data. The model prioritizes this segment because its expected exposure is highest. These breakdowns are evidence of likely drivers, not claimed causes. The manager selects this action, and we record the metric that will validate whether it worked. This closes the loop from data to accountable action.”
12 Out of scope and responsible claims
No LLM/API is used as the core predictive model. Generative AI, if used at all, may only assist non-decision copy and must not affect model scores.
No production deployment, authentication, live integrations, causal guarantees, automated pricing, or automated replenishment.
No claim that the model prevents a cancellation/return; it prioritizes records or segments for review.
No full profit/margin statements unless compatible source cost and realized-price fields are verified.
No model if the provided data cannot support a target or adequate evaluation; show transparent rules and explain the limitation.
